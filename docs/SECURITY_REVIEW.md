# Pre-publication security review

Reviewed on 2026-10-22 for the unpublished WallpaperShell 0.2.0 candidate. Scope: source, staged Git contents, available history, release packaging, local HTTP/native boundaries, defaults and build dependencies. This is a local code review and synthetic regression exercise, not an independent penetration-test certification.

| Finding | Change |
| --- | --- |
| High: wildcard CORS plus an opaque/null origin could expose the bootstrap capability to an untrusted browser document, subject to the browser's local-network protections | Removed wildcard CORS. A null origin cannot bootstrap trust; legacy actions require an already-held capability. The key is no longer exposed through any HTTP endpoint or theme JavaScript file: native document-created injection is restricted to exact top-level pages, and the token file has a protected current-user/SYSTEM Windows DACL. Exact loopback Host/origin checks, cross-site denial, same-origin resource policy and frame protection apply before routing. System telemetry at `/status` and manual speed tests now require the capability too. |
| Privacy: developer-specific weather/location defaults and implicit account/capability discovery | Removed fixed location/time-zone defaults and sibling-profile discovery. Weather, EcoFlow and legacy sharing require explicit app-local opt-in; fresh distributions contain no account files. |
| Privacy: arbitrary renderer diagnostics could be written to disk | Native projection keeps only bounded allowlisted counters, states and flags, with a write-rate limit. Window titles, notification text, account data and free-form payloads are discarded. |
| Medium: build dependencies and CI references could change without byte verification; release build held unnecessary write access | Pinned official Node/WebView2 bytes and full Action commit SHAs, disabled credential persistence, separated read-only build from minimal draft upload. |
| Robustness: constructor output without a newline could grow before line-based limits | Bounded raw output before line parsing; regression covers the unterminated stream. |
| Defense in depth: updater path and token validation, message bounds and static paths | Fail-closed file metadata/reparse handling, whole-value validation, bounded WebView messages, fixed attribution URL and rejection of linked static assets. |

The null-origin risk follows the [browser origin rules](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Access-Control-Allow-Origin); native source/message restrictions follow [Microsoft's WebView2 security guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security). Dependency versions, official evidence and remaining Runtime responsibilities are in [DEPENDENCIES.md](DEPENDENCIES.md).

Verification uses synthetic keys, profiles, notifications, file transactions and isolated loopback requests. No real power command, installer, notification consent or GitHub publication was executed. The Windows dangling-directory junction case is covered; a file-symlink fixture was skipped where the required Windows privilege was unavailable. Generated PNG assets had no EXIF/text metadata. Real incoming notifications and downloaded-update execution are outside this run.

The JavaScript suite completed 405 tests: 404 passed, one private-baseline fixture was explicitly skipped. Additional checks passed for native diagnostics/update boundaries (48), private-key ACL/policy (38), execution of the actual injection script in isolated JavaScript contexts (12), dependency tampering (7), and updater transactions/validation (118). Existing native audio, lifecycle, layout, theme and notification regression checks also passed. Both the main app and category-window host compiled with the shared bootstrap helper. A live check of the installed app confirmed the Luna theme, healthy provider states and capability-protected telemetry; no real category popup was opened for visual verification.

The native host creates a new random capability with the individual user's owner SID and protected DACL in the file-creation operation, before starting the backend. This also supports elevated Windows tokens whose default file owner can be the Administrators group. Existing tokens are preserved and must pass the same strict owner, DACL and format checks; initialization does not silently trust or replace an unsafe token.

Run `bin/node.exe tools/check-security.cjs` before committing/pushing. It checks the worktree and index, then reachable history when present, and emits rule/path metadata rather than secret values. Before this first commit, there was no reachable history. The scanner is pattern-based and cannot prove the absence of every possible secret or every software vulnerability. Export/package checks and the native ZIP/manifest validator provide additional boundaries.

The GitHub repository identity intentionally remains in release/report configuration. No project-wide open-source license has been selected; bundled third-party licenses remain intact. Protect release-account access and installation files. The protected DACL covers only `data/private` and the control key; existing profiles and other runtime data keep their installation-folder permissions. Checksums depend on the trusted GitHub release account and HTTPS; independent publisher signing is not implemented. Other processes running as the same Windows user, or able to replace application code, are outside the application's isolation boundary. Keep the separately installed Evergreen WebView2 Runtime updated. See [PRIVACY.md](PRIVACY.md) for optional connections and local data.
